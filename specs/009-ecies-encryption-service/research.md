# Research: ECIES Transport Encryption

**Feature**: ECIES Transport Encryption in EncryptionService (specs/009-ecies-encryption-service)
**Date**: 2026-06-15
**Normative sources** (in-repo): `specs/gemSpec_Krypt_V2.49.0.pdf` §4.7 (pp. 80–84, Afo A_17220), `specs/gemSpec_COS_V3.14.0.pdf` §6.8.1.4 (ELC Verschlüsselung) / §6.8.2.3 (Asymmetrische Entschlüsselung mittels ELC) / (N085.068). RFC 5652 (CMS), RFC 5083 (AuthEnvelopedData), RFC 5084 (AES-GCM in CMS), BSI TR-03111 (ECKA), gemSpec_OID (`oid_ti_ecies_transport_encryption`).

## Decision 1 — Overall scheme: CMS `AuthEnvelopedData` with per-recipient ECIES key transport

**Decision**: Encode the encrypted document as a CMS **`AuthEnvelopedData`** (`ContentType = id-ct-authEnvelopedData`, OID `1.2.840.113549.1.9.16.1.23`). The document is encrypted once with a random 256-bit AES **transport key** using **AES-256-GCM** (`contentEncryptionAlgorithm = id-aes256-gcm`, OID `2.16.840.1.101.3.4.1.46`; `aes-nonce` = 12-byte IV, `aes-ICVlen`/tag = 16 bytes). The GCM tag is the CMS `mac` field. For each recipient there is one `RecipientInfo` of type **`KeyTransRecipientInfo` (ktri)** with `rid = issuerAndSerialNumber`, `keyEncryptionAlgorithm = oid_ti_ecies_transport_encryption`, and `encryptedKey` = the card-compatible `(PO, C, T)` ASN.1 tuple (Decision 3).

**Rationale**: gemSpec_Krypt §4.7 / A_17220 prescribes exactly this layout and shows the dumped CMS structure (two `RecipientInfo` examples, each `ktri` with `keyEncryptionAlgorithm = oid_ti_ecies_transport_encryption`). gematik deliberately models ECIES as **key transport** (not a CMS `KeyAgreeRecipientInfo`): "Diese Datenstruktur soll konzeptionell so behandelt werden, wie ein RSA-OAEP-Chiffrat eines CEK" — the ephemeral key, ciphertext, and MAC are all bundled inside the opaque `encryptedKey` blob. AES-256-GCM provides the authenticated content encryption (GS-A_4389).

**Alternatives considered**:
- CMS `EnvelopedData` + `KeyAgreeRecipientInfo` (RFC 5753 standard ECDH) — **rejected**: not what §4.7 mandates; the wire bytes and the `keyEncryptionAlgorithm` OID would differ and fail TI interoperability (SC-002/SC-003).
- A bespoke (non-CMS) gematik SEQUENCE — **rejected**: §4.7 explicitly uses CMS for binary data (A_17220) and S/MIME framing; only the `encryptedKey` blob is gematik-specific.

## Decision 2 — ECIES/ELC primitive parameters (gemSpec_COS §6.8.1.4)

**Decision**: Wrap the transport key with the COS **ELC** scheme:
- **Key agreement**: ephemeral-static ECKA-DH per **BSI TR-03111**; ephemeral key pair generated by the sender on the **recipient certificate's named curve**.
- **KDF**: ANSI **X9.63 KDF with SHA-256** over the shared-secret x-coordinate, deriving `K_ENC` (32 bytes, AES-256) and `K_MAC` (CMAC key).
- **Symmetric wrap (`C`)**: **AES-256-CBC** of the transport key with a fixed all-zero IV (single-use derived key).
- **MAC (`T`)**: **AES-CMAC** under `K_MAC` over `C` (truncated tag, 8 bytes as in the §4.7 example).
- **`PO`**: the ephemeral public key as an uncompressed point (`04 || X || Y`).

**Rationale**: §4.7 requires the ECIES parameters to be chosen "dass eine Chipkarte der TI diese unterstützt, d. h. nach [gemSpec_COS#6.8.2.3]" — i.e. identical to what the card performs on decrypt, so a card can unwrap the exact same `(PO,C,T)`. The §4.7 example dump confirms an 8-byte tag and a brainpoolP256r1 ephemeral point. Exact byte layout and CMAC truncation length are pinned against gemSpec_COS during implementation; `ElcCryptogramTest` asserts against the §4.7 example bytes.

**Alternatives considered**: ISO 18033-2 / BC `IESCipher` defaults (HMAC + different KDF) — **rejected**: parameters differ from COS ELC; a TI card could not decrypt the result.

## Decision 3 — Card-compatible `(PO, C, T)` ASN.1 structure

**Decision**: Encode the ECIES cryptogram as the gemSpec_COS "kartenkompatible" structure used by `PSO:DECIPHER`, matching the §4.7 example:

```text
[6] {                                    -- context-tag 6 (0xA6), the COS ELC cryptogram
  OBJECT IDENTIFIER  <named curve>       -- e.g. brainpoolP256r1 (1.3.36.3.3.2.8.1.1.7)
  [APPLICATION 73] { [6] PO }            -- 0x7F49 public-key DO; PO = 04||X||Y (uncompressed point)
  [6] C                                  -- AES-256-CBC ciphertext of the transport key
  [14] T                                 -- AES-CMAC tag (8 bytes)
}
```

This blob is placed verbatim as the CMS `encryptedKey` OCTET STRING of each `ktri`.

**Rationale**: This is precisely the structure a TI card consumes for ELC decryption, so the same bytes decrypt on-card and in software (the whole point of the §4.7 "Metaebene"). Built/parsed with Bouncy Castle `ASN1*` primitives (`DERTaggedObject`, `ASN1ObjectIdentifier`, `DEROctetString`).

**Alternatives considered**: SubjectPublicKeyInfo-wrapped ephemeral key — **rejected**: not card-compatible; the card expects the `[APPLICATION 73]` public-key DO.

## Decision 4 — Decryption seam: JDK `Provider` + `CipherSpi` (resolves the clarification)

**Decision**: Expose ELC decryption through a registered JCE **`Provider` (`ElcSecurityProvider`)** offering `Cipher.getInstance("ELC")`. `EncryptionService` does `cipher.init(DECRYPT_MODE, privateKey); transportKey = cipher.doFinal(encryptedKeyBlob)`. `ElcCipherSpi` dispatches by key type:
- **Software (P12)** — key is a standard `ECPrivateKey`; `SoftwareElcDecryptor` runs ECKA + X9.63-KDF + AES-CBC-decrypt + CMAC-verify via Bouncy Castle.
- **Card (eGK/SMC-B/HBA)** — key is a `CardElcPrivateKey` handle (alias + transport reference, no key bytes); `CardElcDecryptor` (in the PC/SC & SICCT provider modules) sends the `(PO,C,T)` blob via `PSO:DECIPHER` APDUs (gemSpec_COS §6.8.2.3) and returns the transport key.

`EncryptionService` references only `javax.crypto.Cipher` and a `PrivateKey` resolved by alias — it never sees a card.

**Rationale**: Directly satisfies the clarification ("use a CipherSpi that sends APDUs to an encapsulated card; the EncryptionService should not be aware that smart cards are involved") and Principle VIII (adopt the JDK-standard SPI). It mirrors the existing pattern where `KeyStoreAdapter extends KeyStoreSpi`. Two real `ElcDecryptor` implementations justify the seam under Principle I.

**Alternatives considered**:
- Route via the existing `CryptoProvider.decrypt(...)` string-algorithm API — **rejected**: would leak provider/card routing into `EncryptionService` and is not the standard `Cipher` abstraction the clarification mandates (though `CardElcDecryptor` MAY internally reuse the existing card transport).
- A full custom JCE `Provider` for both encrypt and decrypt — **deferred**: encryption needs no SPI dispatch (public-key, software-only), so only the decryption `Cipher` is registered; encryption uses `ElcKeyWrapper` directly.

## Decision 5 — Library evaluation (Principle VII)

**Decision**: Adopt **Bouncy Castle** (`bcpkix-jdk18on`/`bcprov-jdk18on`, already a `crypto-lib` dependency, Apache-2.0, actively maintained, on Maven Central, a constitution "known-good" TI candidate) for: CMS `AuthEnvelopedData` build/parse, AES-256-GCM, EC key agreement, X9.63 KDF, AES-CMAC, brainpool curves, and ASN.1. Custom code is limited to the gematik-specific `(PO,C,T)` card-compatible packaging and the per-recipient `ktri`-with-custom-OID assembly, which no library emits natively.

**Rationale**: Principle VII mandates preferring a vetted library over custom crypto; BC covers every primitive. No new dependency, so no new SBOM entry/CVE review beyond the existing BC monitoring. gemLibPki remains the source for recipient-certificate trust verification (existing `TrustService`).

**Alternatives considered**: Hand-rolled ASN.1/CMS — **rejected** (Principle VII, security risk). Java built-in SunEC only — **rejected**: lacks CMS `AuthEnvelopedData` and brainpool ELC convenience.

## Decision 6 — Standard interface adoption (Principle VIII)

**Decision**: Decryption uses `java.security.Provider` + `javax.crypto.CipherSpi`; key handles implement `java.security.PrivateKey`. No parallel bespoke "Decryptor" interface is exposed to callers — `ElcDecryptor` is an internal dispatch seam, not a public API duplicating JCE. Unneeded `CipherSpi` methods (`engineSetMode`, `engineUpdate` streaming, `engineWrap`/`engineUnwrap` if unused) throw `UnsupportedOperationException` with a descriptive message.

**Rationale**: Principle VIII requires adopting JDK SPIs where they exist; `Cipher`/`CipherSpi`/`Provider` are the JDK standard for exactly this. Confirmed no narrower MicroProfile/Jakarta abstraction applies.

## Decision 7 — Curve support

**Decision**: Support the curve carried by the recipient certificate among **brainpoolP256r1** (primary), **brainpoolP384r1**, **brainpoolP512r1**; reject any other curve (FR-009). Different recipients in one call MAY use different supported curves. Require named-curve encoding of public keys (A_23511); reject explicit-parameter encodings.

**Rationale**: These are the ELC curves TI cards/COS support; brainpoolP256r1 is the §4.7 example. A_23511 forbids explicit-parameter encoding (CVE-2020-0601 mitigation).

**Alternatives considered**: NIST P-256/P-384 — used for TLS (§4.8) but not the ELC card-decryption profile; **rejected** for the transport-key wrap unless a future card profile mandates them.

## Decision 8 — Multi-recipient authenticity caveat (gemSpec_Krypt §4.7.1)

**Decision**: Document — in `EncryptionService` and the contract — that with multiple recipients the shared transport key means any recipient can re-encrypt altered content undetectably; AES-GCM authenticity does **not** bind sender identity across recipients. End-to-end authenticity (e.g. KOM-LE message signature with the SMC-B OSIG key) is the **caller's** responsibility and out of scope here.

**Rationale**: §4.7.1 explicitly calls out this broadcast-encryption limitation. Recording it prevents a false sense of integrity guarantees and is a Principle V (security) obligation.
