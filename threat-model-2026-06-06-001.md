## Threats by Category

### LLM01: Prompt Injection

- **THR-01-001**: speckit-git-feature — User-supplied feature description (`$ARGUMENTS`) is interpolated as a positional argument into a bash shell command without guaranteed sanitization. The advisory escape guidance covers single quotes but not all shell metacharacters; a crafted input can inject arbitrary shell commands executed with the user's local privileges.
  Likelihood: **Med** | Impact: **High** | Risk: **High**
  - Mitigation: The LLM must shell-quote user input using `printf '%q'` or equivalent before interpolating into the script invocation; alternatively, pass the feature description via an environment variable rather than as a positional argument.

- **THR-01-002**: speckit-constitution — The `$ARGUMENTS` field can instruct the skill to read external documents (e.g., PDFs, markdown files), whose content is incorporated verbatim into `.specify/memory/constitution.md`. Document content that mimics instruction format is treated as an LLM directive during constitution generation.
  Likelihood: **Med** | Impact: **Med** | Risk: **Medium**
  - Mitigation: Treat all file-derived content as data, not instructions; apply a structural extraction step (e.g., extract only bullet items or numbered rules) rather than passing raw document text to the generation prompt.

### LLM02: Sensitive Information Disclosure

- **THR-02-001**: speckit-specify, speckit-plan, speckit-implement — These skills produce detailed technical artifacts (functional requirements, security design decisions, cryptographic choices, internal endpoint patterns, data models) stored as plaintext files. When these artifacts are committed and pushed to a public or semi-public repository, system attack surface details are exposed without a pre-publish disclosure review step.
  Likelihood: **Med** | Impact: **Med** | Risk: **Medium**
  - Mitigation: Add a disclosure classification step before any git push; consider marking spec artifacts with a sensitivity label and gating `speckit-git-commit` on human approval when the repository is public.

### LLM03: Supply Chain

- **THR-03-001**: speckit-git-feature, speckit-git-initialize, speckit-git-remote, speckit-git-validate, speckit-implement, speckit-plan — Six skills execute shell scripts sourced directly from `.specify/extensions/git/scripts/bash/` without any integrity check (no checksums, no signatures). If the local `.specify/extensions/` directory is replaced with a tampered version (supply chain compromise, malicious spec-kit release, or repository-write exploit), these scripts execute arbitrary commands under the developer's account.
  Likelihood: **Low** | Impact: **Critical** | Risk: **Medium**
  - Mitigation: Pin the spec-kit extension release to a content-addressed tag and verify a SHA-256 checksum of the scripts directory before execution; alternatively, run scripts in a sandboxed subprocess with restricted filesystem access.

### LLM04: Data and Model Poisoning

- **THR-04-001**: speckit-constitution — `.specify/memory/constitution.md` is loaded as trusted governance context by every other skill. `speckit-constitution` writes new content derived from user arguments and externally sourced documents directly into this file. Adversarial content (from a crafted document or a malicious argument) inserted into the constitution poisons the LLM's governance baseline for the entire project lifetime — all future skills inherit the corrupted rules.
  Likelihood: **Med** | Impact: **High** | Risk: **High**
  - Mitigation: Require explicit human review and approval of all constitution diffs before writing; treat constitution updates as a privileged operation distinct from ordinary skill invocations.

- **THR-04-002**: speckit-specify — User-controlled feature descriptions are written verbatim into `spec.md`, which is subsequently loaded as trusted context by `speckit-plan`, `speckit-tasks`, and `speckit-implement`. Adversarial instruction patterns embedded in a feature description propagate through the full spec-to-implementation pipeline without a sanitization checkpoint.
  Likelihood: **Med** | Impact: **Med** | Risk: **Medium**
  - Mitigation: Apply a structural normalization pass on the feature description before writing to spec.md; reject inputs that match instruction-format patterns (imperative sentences addressed to an AI agent).

### LLM05: Improper Output Handling

- **THR-05-001**: speckit-implement — Task entries in `tasks.md` are produced by LLM-driven `speckit-tasks` and consumed by `speckit-implement` as authoritative implementation instructions, including shell commands, file paths, and dependency operations. LLM-generated task content is executed without a sanitization pass; if a task entry contains an embedded shell command disguised as a description, it may be executed during the implementation phase.
  Likelihood: **Med** | Impact: **High** | Risk: **High**
  - Mitigation: `speckit-implement` must treat task descriptions as text only; shell commands must originate exclusively from the plan's predefined command templates, not from task description strings. Introduce a deny-list for instruction-shaped task descriptions.

### LLM06: Excessive Agency

- **THR-06-001**: speckit-implement — After a single pre-flight checklist gate, `speckit-implement` autonomously executes ALL tasks from `tasks.md` — including file creation, shell commands, package installation, and git operations — without per-task confirmation. One approval bypasses all subsequent execution controls for the entire implementation run, regardless of task count or sensitivity.
  Likelihood: **High** | Impact: **High** | Risk: **Critical**
  - Mitigation: Introduce per-phase (not per-task) confirmation gates before executing each task phase (Setup, Tests, Core, Integration, Polish); for tasks tagged as destructive (file deletion, git resets, external network calls), require individual user approval.

- **THR-06-002**: speckit-constitution, speckit-implement, speckit-plan, speckit-specify — Mandatory extension hooks (`optional: false`) auto-execute via `EXECUTE_COMMAND` without per-hook user confirmation. Hook chains defined in `extensions.yml` allow hook authors to inject arbitrary skill invocations into any workflow step without the user seeing or approving the intermediate executions.
  Likelihood: **Med** | Impact: **High** | Risk: **High**
  - Mitigation: Demote all hooks to `optional: true` by default; require explicit user confirmation before any `EXECUTE_COMMAND` dispatch; audit `extensions.yml` as part of the repository's security review process.

### LLM07: System Prompt Leakage

- **THR-07-001**: All 16 skills (systemic) — All SKILL.md instruction files are committed as plain-text workspace files in `.claude/skills/`. Any collaborator with repository read access — or anyone who clones a public fork — can inspect the full prompt engineering patterns, hook orchestration logic, and internal execution behaviors. This reduces the effort required to craft targeted prompt injection attacks calibrated to the observed skill structure.
  Likelihood: **High** | Impact: **Low** | Risk: **Medium**
  - Mitigation: This is partially by-design (skills are open-source spec-kit artifacts). For organization-specific prompt customizations, store those in a separate private overlay rather than in the shared `.claude/skills/` directory; document that SKILL.md files should be treated as public artifacts.

### LLM08: Vector and Embedding Weaknesses

No threat detected. (Skills do not use RAG pipelines, embedding stores, or vector databases; `.specify/memory/constitution.md` is flat-text context loaded by reference, not a vector embedding, and no unvalidated retrieval step is present.)

### LLM09: Misinformation

- **THR-09-001**: speckit-analyze, speckit-checklist — These skills generate pass/fail validation assessments using only LLM analysis with no external oracle or deterministic rule engine. A hallucinated "pass" verdict for a non-compliant requirement propagates undetected through the pipeline, potentially allowing a defective specification to proceed to plan and implementation phases.
  Likelihood: **Med** | Impact: **Med** | Risk: **Medium**
  - Mitigation: Supplement LLM-based validation with deterministic rule checks (e.g., regex for mandatory section headers, FR count assertions); require a second-pass human review before any checklist item is marked complete.

- **THR-09-002**: speckit-specify — In safety-critical or regulatory domains (e.g., healthcare TI-Platform, gematik normative specifications), LLM-generated functional requirements may plausibly misinterpret normative requirements without any validation flag. The pipeline provides no mechanism to detect domain-knowledge errors before a spec proceeds to planning and implementation, and incorrect FRs in healthcare contexts carry patient safety or regulatory non-compliance risk.
  Likelihood: **Med** | Impact: **High** | Risk: **High**
  - Mitigation: For regulated domains, require a domain-expert review gate before a spec exits Draft status; add a mandatory checklist item confirming normative source cross-reference for each FR.

### LLM10: Unbounded Consumption

- **THR-10-001**: speckit-implement — No upper bound on the number of tasks processed in a single invocation. A `tasks.md` with an adversarially large task count or recursive task self-references causes the skill to run until the LLM token limit or billing ceiling is reached, with no built-in circuit breaker or task-count cap.
  Likelihood: **Low** | Impact: **Med** | Risk: **Low**
  - Mitigation: Add a configurable maximum task count (default: 100); halt and prompt the user if `tasks.md` exceeds this threshold; detect and reject circular task references at parse time.

- **THR-10-002**: speckit-constitution, speckit-implement, speckit-plan, speckit-specify — Mandatory `after_*` hooks can chain into other skills that themselves define mandatory `after_*` hooks, forming an unbounded invocation cycle if `extensions.yml` is misconfigured (e.g., `after_specify` → speckit-plan → `after_plan` → speckit-implement → ...). No cycle-detection or max-depth guard is described in the hook dispatch logic.
  Likelihood: **Low** | Impact: **Med** | Risk: **Low**
  - Mitigation: Implement a hook invocation depth counter (max depth: 3); detect and break cycles by tracking active skill invocations in the session context; emit a warning and halt rather than looping indefinitely.
